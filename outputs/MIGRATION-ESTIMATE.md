# 炉石旅人 Web → Godot 完整迁移成本估算

估算日期：2026-09-24

## 结论

当前 Godot 主线已经完成 P0、大部分 P1/P2/P3，但“完整迁移”不能按当前可运行状态收尾。
按 Web 原版功能、93 张基础卡、10 个种族和 52 个独立效果计算，必须分开看“功能迁移成本”和“旧工作方式造成的浪费”：

| 口径 | 人日 | 双线程目标 Token | 新会话数 | 说明 |
|---|---:|---:|---:|---|
| 只补齐规则与核心可玩闭环 | 15-25 | 1500-4000 万 | 6-12 | 能完整游玩，表现层不逐卡验收 |
| 完整迁移到逐卡六层闭环 | 30-50 | 8000-1.8 亿 | 15-30 | 规则、事件、UI、动画、音频和证据逐项收口 |
| 继续沿用长会话、主会话读图、压缩后硬撑的旧方式 | 30-50 | 2.9-5.2 亿 | 25-40 | 这是流程浪费，不是迁移固有成本 |
| 另做原创美术、完整机制音效和商店发行材料 | 再加 15-30 | 再加 5000 万-1.2 亿 | 再加 8-15 | Web 原版没有这些资产 |

推荐用于排期和预算的控制值：

- 功能迁移：**约 15-25 个人日，1500-4000 万 Token，6-12 个新会话**。
- 完整六层迁移：**约 30-50 个人日，8000 万-1.8 亿 Token，15-30 个新会话**。
- AI 辅助下的完整迁移日历工期：约 **12-20 个专注工作日**。
- 旧的 3.1 亿 Token 记录是反面成本锚点，不应直接拿来预算。

## 价格区间

价格来源：DeepSeek 官方中文定价页，2026-09-24 核验。实际模型使用 `deepseek-flash`，旧的 `deepseek-v4-flash` 会路由到 DeepSeek-V4.1-Flash，并按 Flash 价格计费。

| deepseek-flash | 缓存命中输入 / 百万 | 缓存未命中输入 / 百万 | 输出 / 百万 |
|---|---:|---:|---:|
| 空闲时段 | ¥0.02 | ¥1 | ¥4 |
| 高峰时段 | ¥0.04 | ¥2 | ¥8 |

高峰时段为 UTC 周一至周五 `01:00-04:00`、`06:00-10:00`。换算北京时间为工作日 `09:00-12:00`、`14:00-18:00`。晚间、午休、早上 9 点前、周末和中国法定节假日均为空闲价。

下面价格按两组极端估算：

- 低估计费：90% 输入缓存命中、5% 输出、空闲时段。
- 高估计费：75% 输入缓存命中、10% 输出、高峰时段。

| 迁移口径 | Token | 低估计费 | 高估计费 | 建议预算 |
|---|---:|---:|---:|---:|
| 功能迁移 | 1500-4000 万 | ¥5 | ¥51 | ¥15-30 |
| 完整六层迁移 | 8000 万-1.8 亿 | ¥25 | ¥230 | ¥60-120 |
| 旧长会话方式 | 2.9-5.2 亿 | ¥91 | ¥664 | 不建议 |
| 旧会话实际记录 | 311,804,318 | ¥96 | ¥192 | 仅供参考 |
| 另加原创美术与机制音效 | 5000 万-1.2 亿 | ¥16 | ¥153 | ¥30-80 |

如果改用 `deepseek-v4-pro`，缓存命中输入、未命中输入和输出价格分别约为 Flash 的 7.5 倍、4.5 倍和 3.4 倍。整体账单通常约为 Flash 的 3.5-7.5 倍，不建议让 Pro 承担日常批量迁移。

这条日志说明旧工作方式的成本主要被图片、上下文重载和压缩放大。640 条图片输入和 385 次压缩意味着同一段工程背景被反复装入上下文，消耗会放大数倍。

直接复制这条日志当预算是错误的。当前更可控的目标应按 **功能迁移 1500-4000 万 Token、完整六层迁移 8000 万-1.8 亿 Token** 规划：

- 固定前缀只读 `AGENTS.md`、`SESSION-HANDOFF.md`、`VISION-FACTS.md`。
- 每个会话只做一个机制族或一个交付切片，完成后立即落盘换会话。
- 主会话零图片，普通识图走脚本，主观审图另开会话。
- 优先批处理同一种族的卡，不按单卡重复重建上下文。
- 已有 9,451 行 GDScript 和 15/15 parity 应作为脚手架复用，不重新生成。

## 推荐执行方式

### 模型分工

- 默认全部使用 `deepseek-flash`。
- `deepseek-v4-pro` 只用于 G1-G3 架构定案、G5 统一效果分发表、连续两轮无法定位的 parity 根因。
- Pro 消耗控制在总 Token 的 10% 以内，不允许让 Pro 扫描大文件或逐卡润色。
- 视觉只走 `deepseek-v4-flash-vision-exp` 短任务；主会话保持零图片。

### 会话预算

- 单会话控制指标改为“缓存未命中输入 + 输出”不超过 150 万。
- 总 Token 可以超过 600 万；缓存命中输入很便宜，不应和未命中输入混成一个停止线。
- 单会话只处理一个机制族、一个根因或一个界面闭环。
- 同一失败原因最多修正两次；第二次仍失败就改做最小复现，不继续扩大上下文。
- 每次工具输出控制在 12,000 Token 内，禁止全仓扫描和整读大文件。

### 推荐阶段

| 阶段 | 内容 | 会话数 | Token预算 |
|---|---|---:|---:|
| 0 | 冻结 Web 基准，确认迁移层级与验收口径 | 1 | 100-200 万 |
| A | G1-G3 攻击生命周期、受击流水线、跨阶段运行态 | 3-4 | 1500-3000 万 |
| B | G4-G5 开场预扫描和统一效果分发表，关闭 17 条规则缺口 | 2-3 | 1000-2000 万 |
| C | 10 个种族按族批处理卡级规则和断言，不按单卡开会话 | 8-12 | 3000-6000 万 |
| D | UI、动画、音频和跨战斗状态按机制族收口 | 4-6 | 2000-4000 万 |
| E | parity、截图/录屏证据、性能、输入和桌面打包 | 2-3 | 1000-2000 万 |
| 合计 | 完整六层迁移 | 20-30 | 8500 万-1.7 亿 |

阶段 A 实测：总 Token 约 3510 万，其中缓存命中约 3459 万，缓存未命中约 35.2 万，输出约 14.9 万。原始总 Token 高于 1500-3000 万预算，但昂贵部分仅约 50.1 万，Flash 空闲价约 ¥1.64。说明成本应主要按缓存未命中输入和输出控制，不应把缓存命中重复计量当成主要成本。

阶段 B 实测增量与 A+B 累计：

- 阶段 B 增量：约 4900 万总 Token；缓存未命中约 9.3 万，输出约 6.5 万。
- 阶段 A+B 累计：约 8410 万总 Token；缓存命中约 8345 万，缓存未命中约 44.5 万，输出约 21.4 万。
- A+B 空闲价约 ¥2.97，高峰约 ¥5.94。
- 阶段 C 增量：约 7980 万总 Token；缓存未命中约 5.9 万，输出约 7.3 万。
- 阶段 A+B+C 累计：约 1.639 亿总 Token；缓存命中约 1.6315 亿，缓存未命中约 50.4 万，输出约 28.7 万。
- A+B+C 空闲价约 ¥4.92，高峰约 ¥9.83。
- 阶段 D（全部机制族）增量：约 1.175 亿总 Token；缓存未命中约 7.7 万，输出约 8.9 万，费用增量约 ¥2.78。
- 阶段 A+B+C+D 累计：约 2.815 亿总 Token；缓存命中约 2.805 亿，缓存未命中约 58.1 万，输出约 37.7 万。
- A+B+C+D 空闲价约 ¥7.70，高峰约 ¥15.40。

阶段 A 未通过前不进入阶段 C。逻辑规则未稳定前，不用动画和音效掩盖结算问题。

### 缓存与时间安排

- 固定只读前缀顺序为 `AGENTS.md`、`SESSION-HANDOFF.md`、`VISION-FACTS.md`，中途不改格式。
- 用追加式交接，不重写历史总结；相同任务描述尽量复用，提升前缀缓存命中率。
- Flash 的空闲缓存命中输入比高峰未命中输入便宜 100 倍。批量编码、测试和重构安排在北京时间晚间、午休、早上 9 点前、周末或节假日执行。
- 需要高判断力的少量架构任务可以放在高峰时段，但日常批量迁移不应长期在高峰运行。

### 验收门槛

1. 每批先过规则和事件，再补 UI、动画、音频和证据。
2. 每批必须有可执行测试、事件计数或截图/录屏证据，不能只写“已实现”。
3. 完成后立即回填 `SESSION-HANDOFF.md`、`VISION-FACTS.md` 和 `docs/MIGRATION-PARITY.md`。
4. 发生上下文压缩就结束当前里程碑，不继续编码。

## 估算边界

- 包含 Web 原版已有功能、93 张基础卡、10 个种族、桌面端运行和基础发行准备。
- 不包含多人联机、新战役、新种族、完整商业美术和平台商店上线。
- 若 Web 原版未来继续加卡或改机制，Godot 仍未迁移部分同步涨价，已完成部分按差异增量计算。
- Token 是 Codex 上下文消耗，不等于人民币或美元账单。金额需按实际模型的输入、缓存输入和输出单价另算。
